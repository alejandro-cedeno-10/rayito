## 2. `run-microvm`

Fuente: `docs/aws-api/model_summary.md` (RunMicrovm), `docs/aws-api/cli/run-microvm.txt`,
<https://docs.aws.amazon.com/lambda/latest/dg/microvms-launching.html>.

**Input `RunMicrovmRequest`**

| Campo | Tipo / restricción | Notas |
|---|---|---|
| `imageIdentifier`* | string 1–256 | ARN de la imagen (`arn:aws:lambda:<region>:<acct>:microvm-image:<name>`); el nombre pelado no vale en ninguna operación (**medido 2026-09-15**) |
| `imageVersion` | string | por defecto la última versión `ACTIVE` |
| `executionRoleArn` | ARN de rol IAM | opcional; sin él no hay credenciales dentro de la VM **ni logs de runtime** |
| `idlePolicy` | struct opcional; si está presente los 3 campos son obligatorios | `maxIdleDurationSeconds` (min 60; docs: max 28800), `suspendedDurationSeconds` (min 0; 0 = terminar al suspender), `autoResumeEnabled` (bool) |
| `logging` | `{"disabled":{}}` \| `{"cloudWatch":{"logGroup","logStream"}}` | |
| `runHookPayload` | string 0–4096 (modelo), `sensitive: true` | entregado en el body del hook `/run` |
| `maximumDurationInSeconds` | int 1–28800 | running **+ suspended** desde `startedAt` |
| `ingressNetworkConnectors` / `egressNetworkConnectors` | listas de ARN (máx 10) | `ALL_INGRESS`, `NO_INGRESS`, `SHELL_INGRESS`, `INTERNET_EGRESS` gestionados por AWS: `arn:aws:lambda:<region>:aws:network-connector:aws-network-connector:<NAME>` |
| `clientToken` | string 1–128, `idempotencyToken` | botocore genera uuid4 si se omite |

**Output `RunMicrovmResponse`**: `microvmId`*, `state`* (`PENDING` al volver), `endpoint`* (hostname **sin esquema**, **medido 2026-09-15**: `<uuid>.lambda-microvm.us-east-1.on.aws`), `imageArn`*, `imageVersion`* (`1.0`, `2.0`, …), `executionRoleArn`, `idlePolicy`, `maximumDurationInSeconds`*, `startedAt`*, `terminatedAt`, `stateReason`, `ingressNetworkConnectors`, `egressNetworkConnectors`.

**Errores**: `ValidationException` 400, `AccessDeniedException` 403, `ResourceNotFoundException` 404, `ConflictException` 409, `ServiceQuotaExceededException` (cuota de memoria; **HTTP 402**), `ThrottlingException` 429 (`retryAfterSeconds`), `InternalServerException` 500. botocore ≥ 1.43.82 añade `InsufficientCapacityException` (500, no está en el modelo de la CLI 2.36.23).

Hechos que cambian el diseño:
- **No hay parámetro de variables de entorno en `run-microvm`.** Las `environmentVariables` viven en la imagen (máx 50) y las comparten todos los MicroVMs. El **único canal per-VM** es `runHookPayload`.
- **El tamaño (memoria/vCPU) se fija en la imagen**, no aquí.
- Prefijo del `microvmId`: **`microvm-<uuid>`** (**medido 2026-09-15**; ni `mvm-` ni `ai-`). No parsear el prefijo.
- Latencias (**medido 2026-09-15**, 2 GB, us-east-1): llamada API 0.2–0.75 s; **primer 200 en el endpoint p50 1.85 s / p95 2.13 s** (20 secuenciales). **20 `run-microvm` simultáneos: 20/20 OK sin `ThrottlingException`** con un cliente sin reintentos; la API responde más lenta (p50 1.37 s) en vez de rechazar; primer 200 p50 2.53 s / p95 3.59 s. Mantener igualmente un token bucket de 5/s en el SDK.
- Un `/suspend` que devuelve 500 **termina** la VM (**medido 2026-09-15**, ver §5 y §8).

## 3. `create-microvm-auth-token`

Fuente: `docs/aws-api/model_summary.md`, `docs/aws-api/cli/create-microvm-auth-token.txt`,
<https://docs.aws.amazon.com/lambda/latest/dg/microvms-networking.html>.

| Campo | Restricción |
|---|---|
| `microvmIdentifier`* | string 1–256 (URI) |
| `expirationInMinutes`* | int min 1; **máx 60** (**medido 2026-09-15**: 61 → `ValidationException` "ExpirationMinutes 61 exceeded max allowed of 60.") |
| `allowedPorts`* | lista (min 1) de `{"port": N}` \| `{"range": {"startPort": N, "endPort": M}}` \| `{"allPorts": {}}` |

Respuesta: `authToken` es un **map** `AuthTokenKey → AuthTokenValue` (1–10 entradas, valores hasta 8000 chars). **medido 2026-09-15**: una única clave, exactamente **`X-aws-proxy-auth`**; su valor es el JWE que va en la cabecera del mismo nombre. Tolerar otras claves.

- Token ligado a un MicroVM, a los puertos permitidos y a la expiración. No hay modo sin autenticación.
- Cuota: 50 TPS por cuenta/región. Cachear por sandbox, nunca acuñar por llamada.
- Un token acuñado antes de suspender sigue siendo válido tras reanudar (**medido 2026-09-15**); la expiración es en reloj de pared, así que el refresher debe seguir corriendo durante la pausa.
- La expiración **sólo se evalúa al abrir la conexión**: un stream abierto con un token de 1 minuto siguió recibiendo datos 150 s (**medido 2026-09-15**). Un token expirado no corta streams vivos; el refresher sólo tiene que llegar antes de la siguiente conexión nueva.
- `create-microvm-shell-auth-token` (`expirationInMinutes`*, 5 TPS) requiere el conector `SHELL_INGRESS`; abre un WebSocket en el puerto 8022 con subprotocolos `lambda-microvms`, `lambda-microvms.authentication.<token>`, `lambda-microvms.port.8022` y entra **como root** en el contenedor de la app. AWS recomienda deshabilitarlo en producción.

## 4. `create-microvm-image` y ciclo de vida de imágenes

Fuente: `docs/aws-api/model_summary.md` (CreateMicrovmImage), `docs/aws-api/cli/create-microvm-image.txt`,
<https://docs.aws.amazon.com/lambda/latest/dg/microvms-images.html>.

**Input `CreateMicrovmImageRequest`**

| Campo | Restricción | Notas |
|---|---|---|
| `name`* | 1–64, `[a-zA-Z0-9-_]+`, único por cuenta | |
| `baseImageArn`* | `arn:aws:lambda:<region>:aws:microvm-image:al2023-1` | descubrir con `list-managed-microvm-images` |
| `baseImageVersion` | string | fijarla explícitamente en CI (supply chain) |
| `buildRoleArn`* | ARN | necesita `s3:GetObject` del artefacto + `logs:*` (+ `ecr:*` si `FROM` privado) |
| `codeArtifact`* | `{"uri": "s3://bucket/key.zip"}` | zip con el `Dockerfile` **en la raíz**; mismo region que la imagen |
| `resources` | lista máx 1 de `{"minimumMemoryInMiB": N}` | **aquí se fija el tamaño**; docs lo llaman "memory" |
| `cpuConfigurations` | lista de `{"architecture": "ARM_64"}` | único valor |
| `environmentVariables` | map, máx 50, clave ≤256, valor ≤4096 | nivel imagen, congeladas en el snapshot |
| `additionalOsCapabilities` | `["ALL"]` único valor | mounts, netns, eBPF, iptables dentro de la VM. **Medido (M6, §16 Q47/Q48)**: `CapEff` completo para root y cgroup2 montado, pero el kernel del guest no trae `xt_owner` (sin módulos cargables): `iptables -m owner` es imposible; `ip rule … uidrange` sí funciona |
| `hooks` | ver §8 | `port` + `microvmHooks` + `microvmImageHooks` |
| `logging`, `egressNetworkConnectors` (máx 1), `description`, `tags`, `clientToken` | | |

**Output**: `imageArn`*, `name`*, `state`*, `imageVersion`*, `latestActiveImageVersion`, `latestFailedImageVersion`, `createdAt`*, `updatedAt`, y eco de la configuración.

**Tamaños** (baseline → pico 4x, disco):

| `minimumMemoryInMiB` | baseline | pico | disco | ancho de banda endpoint |
|---|---|---|---|---|
| 512 | 0.5 GB / 0.25 vCPU | 2 GB / 1 vCPU | 8 GB | 1 MB/s |
| 1024 | 1 GB / 0.5 vCPU | 4 GB / 2 vCPU | 8 GB | 2 MB/s |
| 2048 (default) | 2 GB / 1 vCPU | 8 GB / 4 vCPU | 8 GB | 4 MB/s |
| 4096 | 4 GB / 2 vCPU | 16 GB / 8 vCPU | 16 GB | 8 MB/s |
| 8192 | 8 GB / 4 vCPU | 32 GB / 16 vCPU | 32 GB | 16 MB/s |

**Cómo construye AWS la imagen**: descarga el zip → arranca una VM desde la base gestionada → ejecuta el `Dockerfile` → lanza `ENTRYPOINT`/`CMD` → espera `/ready` (si está habilitado) → **snapshot de memoria + disco** → opcionalmente arranca una VM nueva y llama `/validate`, muestreando las páginas tocadas para prefetch. Lo que esté en memoria antes de `/ready` queda en el snapshot y **es idéntico en todos los MicroVMs** (ver §15).

**Estados** (enums del modelo):
- `MicrovmImageState`: `CREATING, CREATED, CREATE_FAILED, UPDATING, UPDATED, UPDATE_FAILED, DELETING, DELETE_FAILED, DELETED`
- `MicrovmImageVersionState`: `PENDING, IN_PROGRESS, SUCCESSFUL, FAILED, DELETING, DELETED, DELETE_FAILED`
- `MicrovmImageVersionStatus`: `ACTIVE, INACTIVE` (lo cambia el usuario con `update-microvm-image-version --status`)
- `BuildState`: `PENDING, IN_PROGRESS, SUCCESSFUL, FAILED`

Para lanzar: imagen `CREATED|UPDATED` **y** versión `SUCCESSFUL` **y** status `ACTIVE`. Los tres estados son independientes.

`get-microvm-image-build` devuelve `buildState`, `architecture=ARM_64`, `chipset=GRAVITON`, `chipsetGeneration`, `stateReason` y `snapshotBuild{memorySnapshotSizeInBytes, codeInstallSizeInBytes, diskSnapshotSizeInBytes}` (base del coste de snapshot y del tiempo de arranque). **medido 2026-09-15** para la imagen sonda (Python 3.12 + ipykernel precargado, 2048 MiB): build **135–145 s** de `create/update` a `SUCCESSFUL`; memoria 672–678 MB, `codeInstallSizeInBytes` 644 MB, disco 33–35 MB; `chipsetGeneration` fue `3` en una build y `4` en otra (no se elige).

Otros hechos **medido 2026-09-15**: las versiones se numeran `1.0`, `2.0`, `3.0`; `baseImageVersion` en la respuesta es `1.0` aunque `list-managed-microvm-image-versions` liste `0` y `1`; `get-microvm-image`, `update-microvm-image` y el resto exigen el **ARN** en `imageIdentifier` (el nombre → `ValidationException: Invalid ARN format`); `update-microvm-image-version --status INACTIVE` funciona, pero mientras la imagen está `UPDATING` (otra versión en build) responde `ConflictException: MicroVM Image is already in state: UPDATING`.

Errores de build documentados: `S3_ACCESS_DENIED, S3_NO_SUCH_KEY, S3_NO_SUCH_BUCKET, S3_INVALID_OBJECT, S3_CROSS_REGION_ACCESS_DENIED, ARCHIVE_DOCKERFILE_NOT_FOUND, ARCHIVE_INVALID, CONTAINER_BUILD_FAILED, DISK_STORAGE_FULL, INTERNAL_PLATFORM_ERROR`. **Medido (M6)**: si `/validate` no responde, `stateReason` = `Validate hook invocation timed out after PT10M` y la versión queda `FAILED/INACTIVE` (la imagen `UPDATE_FAILED`); `/ready` puede haber respondido 200 igualmente.

`delete-microvm-image-version` (**medido 2026-09-16**, §16 Q49): borra una versión `SUCCESSFUL/ACTIVE` o `FAILED/INACTIVE` directamente (no hace falta `--status INACTIVE` antes); la imagen pasa a `UPDATING` y la versión a `DELETING`, y en ≈ 5,4 s la versión desaparece (`ResourceNotFoundException`) y la imagen vuelve a `UPDATED`. Encadenar borrados sin esperar produce `ConflictException`; `scripts/image_prune.py` espera a que la imagen salga de `UPDATING`/`DELETING` entre borrados (0 conflictos en 6 borrados) y reintenta con 5/10/20/40/80 s si aun así aparece. `delete-microvm-image` acepta una imagen con versiones `ACTIVE` y responde `state=DELETING` en el acto.

`update-microvm-image` es **PUT**: `codeArtifact`, `baseImageArn` y `buildRoleArn` son obligatorios en cada llamada aunque sólo cambie el zip. Cada update crea una versión nueva (cuota: 50 versiones por imagen, 100 imágenes, 5 builds concurrentes; 10 en esta cuenta). Tiempo de build: 4–6 min según aws-samples *(tercero)*; **135–145 s** para la imagen sonda (**medido 2026-09-15**).

Base de contenedor: `public.ecr.aws/lambda/microvms:al2023-minimal` (sin `tar`, `gzip`, `procps`; trae OpenSSL parcheado para reseed tras snapshot). Cualquier `FROM` Linux ARM64 vale si es "snapshot compatible". Versiones de la base gestionada: `AVAILABLE → DEPRECATED (60 d) → EXPIRING (30 d) → EXPIRED (no arranca) / RECALLED`.

CloudFormation: `AWS::Lambda::MicrovmImage` (`Name, BaseImageArn, BuildRoleArn, CodeArtifact.Uri, CpuConfigurations, Resources[MinimumMemoryInMiB], Hooks{Port, MicrovmHooks, MicrovmImageHooks}, EnvironmentVariables, Logging`) y `AWS::Lambda::NetworkConnector`.

## 5. `suspend-microvm` / `resume-microvm` / `terminate-microvm`

Fuente: `docs/aws-api/model_summary.md`, `docs/aws-api/cli/{suspend,resume,terminate}-microvm.txt`.

- Input único: `microvmIdentifier`*. Respuesta vacía. Los tres están marcados `idempotent`; `terminate` sobre un MicroVM ya terminado devuelve éxito.
- `suspend` sólo desde `RUNNING`; `resume` sólo desde `SUSPENDED`; si no → `ConflictException` 409 (docs). **Medido 2026-09-16 (M5, §16 Q38)**: `suspend-microvm` sobre un VM ya `SUSPENDED` y `resume-microvm` sobre uno `RUNNING` responden **200** (idempotentes, sin `ConflictException`); el `resume` repetido no sube `resume_generation`. El SDK lee `get-microvm` antes de suspender para que `pause()` devuelva `False` sobre un VM suspendido.
- Cuotas: SuspendMicrovm **2 TPS**, ResumeMicrovm 5 TPS, TerminateMicrovm 10 TPS.
- Suspender = hook `/suspend` → checkpoint de memoria + disco. Reanudar = restaurar → hook `/resume` (la VM sigue `SUSPENDED` mientras corre) → `RUNNING` al devolver 200.
- Tiempos (**medido 2026-09-15**, 2 GB): `suspend-microvm` → `SUSPENDED` en 1.4 s; `resume-microvm` API 0.6 s y **primer 200 a 1.2 s** de la llamada; con `autoResumeEnabled`, el primer request a una VM suspendida vuelve con 200 en **1.1–1.6 s**.
- **Si `/suspend` devuelve 500 la VM se termina** (**medido 2026-09-15**): `suspend-microvm` acepta, en < 5 s el estado es `TERMINATED`, el endpoint da 502 y `stateReason` = "Suspend lifecycle hook returned HTTP status 500. Please check your hook endpoint and application logs for more details." No se observaron reintentos. `rayd` debe responder 200 a `/suspend` pase lo que pase.
- Con `autoResumeEnabled=true`, el primer request al endpoint reanuda la VM y AWS retiene el request; si falla → **502**.
- El tiempo suspendido **cuenta** para `maximumDurationInSeconds` (máx 8 h, no ajustable).

## 6. `get-microvm` / `list-microvms` y máquina de estados

Fuente: `docs/aws-api/model_summary.md`, `docs/aws-api/cli/get-microvm.txt`,
<https://docs.aws.amazon.com/lambda/latest/dg/microvms-how-it-works.html>.

`MicrovmState`: `PENDING, RUNNING, SUSPENDING, SUSPENDED, TERMINATING, TERMINATED`.

```
PENDING ──(/run 200)──► RUNNING ──(idle o API)──► SUSPENDING ──(/suspend + checkpoint)──► SUSPENDED
   │ (/run falla o timeout)     ▲                                                        │
   ▼                            └────────(tráfico con autoResume, o resume-microvm)──────┘
TERMINATING ◄── RUNNING (API o maximumDuration) / SUSPENDED (suspendedDurationSeconds o API)
   │ (/terminate)
   ▼
TERMINATED   (stateReason lleva el motivo)
```

- **`get-microvm` es eventualmente consistente** (texto literal de la API: "determine readiness by connecting to the endpoint"). El SDK debe sondear el endpoint (p. ej. `HealthService.Health`), no el estado. GetMicrovm: 100 TPS. **medido 2026-09-15 (M1)**: nada más volver `terminate-microvm`, `get-microvm` aún responde `RUNNING`; `TERMINATING` a los 0.14 s y `TERMINATED` (`stateReason` "Success.") segundos después. Los tests sondean con plazo, nunca leen el estado una sola vez.
- `GetMicrovmResponse`: mismos campos que `RunMicrovmResponse`.
- `list-microvms`: filtros `imageIdentifier`, `imageVersion`; `maxResults` 1–50; los items sólo traen `microvmId, state, imageArn, imageVersion, startedAt` (**sin `endpoint`**). Los `TERMINATED` **siguen apareciendo** al menos ~20 min (**medido 2026-09-15**: 45 entradas TERMINATED de la misma imagen tras la pasada). `get-microvm` sobre uno terminado responde `state=TERMINATED`, `stateReason="Success."`, `terminatedAt`. El SDK filtra por estado.

## 7. Endpoint del MicroVM (plano de datos)

Fuente: <https://docs.aws.amazon.com/lambda/latest/dg/microvms-networking.html>,
<https://docs.aws.amazon.com/lambda/latest/dg/microvms-launching.html>,
<https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html>.

- URL: `https://<endpoint>/…` con `endpoint = <id>.lambda-microvm.<region>.on.aws`. TLS siempre termina en el proxy de AWS; la app dentro puede servir texto plano.
- **medido 2026-09-15**: el proxy corre **dentro de la VM**: la app ve `client=127.0.0.1`, `Host: <endpoint>`, un `x-amzn-requestid` y las cabeceras del cliente; ninguna `X-aws-proxy-*` ni `X-Forwarded-For`. Por eso un listener en `127.0.0.1` también es alcanzable vía `X-aws-proxy-port` (Q18) y **el puerto de hooks (9000) es alcanzable con un token `allPorts`** (Q24): nunca incluirlo en `allowedPorts`.
- Cabeceras del proxy (namespace reservado `X-aws-proxy-*`; **AWS las elimina antes de reenviar**, la app nunca las ve):
  - `X-aws-proxy-auth: <JWE>` — obligatoria.
  - `X-aws-proxy-port: N` — puerto destino; por defecto **8080**; debe estar en `allowedPorts` o **403**.
  - `X-aws-proxy-force-h2: true` — **necesaria para que el proxy hable HTTP/2 con una app en texto plano** (gRPC lo exige). **medido 2026-09-15**: sin la cabecera el cliente negocia HTTP/2 con el proxy pero la app recibe HTTP/1.1; con ella el proxy pasa a h2c y una app sólo-HTTP/1.1 responde **502**. Alternativa: que la app sirva TLS con ALPN h2. **medido 2026-09-15 (M1)**: contra `rayd` (tonic h2c) un unario gRPC responde OK con trailers **con y sin** la cabecera (§16 Q17); el SDK la envía siempre de todos modos.
  - En HTTP/2 y en metadata gRPC las claves van en minúsculas (`x-aws-proxy-auth`, RFC 9113 §8.2); el proxy ya recibe así los ejemplos `curl --http2` de la propia documentación.
- WebSocket: subprotocolos `lambda-microvms`, `lambda-microvms.authentication.<token>`, `lambda-microvms.port.N` (AWS los elimina antes de reenviar).
- Protocolos: HTTP/1.1, HTTP/2 (ALPN), WebSocket, gRPC, SSE.
- Errores del proxy (no de la app): **400** cabecera/subprotocolo de puerto inválido; **403** token ausente/expirado/inválido o puerto no permitido; **429** rate limit (cuenta o por-VM); **500**; **502** app no responde, o auto-resume falló tras los reintentos, o primeros segundos tras `run-microvm` mientras se restaura el snapshot.
- Límites **no ajustables** por MicroVM: conexiones concurrentes 8 (1 vCPU), 16 (2), 32 (4), 64 (8), 128 (16); requests/s 40 (4 vCPU/8 GB) y 160 (16 vCPU/32 GB) — Service Quotas tampoco publica el valor a 1–2 vCPU (**medido 2026-09-15**). **medido 2026-09-15**: 9 streams HTTP/1.1 simultáneos de 30 s a 2 GB recibieron 9 × 200, sin 429; el cap de 8 no se aplicó como rechazo en esa prueba. Ancho de banda: tabla de §4 (entrada + salida); **medido 2026-09-15** 4.54 MB/s bajando 16 MiB a 2 GB.
- **Subida en HTTP/2 limitada por ventana** (**medido 2026-09-15**, M3, §16 Q32): el proxy anuncia al cliente una ventana de control de flujo de 64 KiB por conexión y no la crece, así que cualquier subida HTTP/2 (gRPC client-stream o `POST` h2) rinde ≈ una ventana por RTT del cliente (0,53–0,68 MB/s a 93 ms), también con varios streams en paralelo; un `POST` HTTP/1.1 por el mismo proxy alcanza los 4–4,9 MB/s de la tabla y la bajada HTTP/2 6,7 MB/s. La ventana que anuncia la app (tonic) al proxy no cambia nada.
- Idle: **sólo cuentan los bytes que cruzan el endpoint**; actividad saliente no cuenta. **medido 2026-09-15**: un stream con un mensaje por segundo mantuvo la VM `RUNNING` 260 s con `maxIdleDurationSeconds=120`; un stream **abierto sin mensajes** no cuenta: la VM pasó a `SUSPENDED` a los ~130 s, el cliente vio la conexión cortada (`Response ended prematurely`) unos 57 s después y el siguiente request auto-reanudó en 1.1 s. Un PTY/stream ocioso no mantiene viva la VM; el SDK necesita keepalives con datos si quiere evitarlo.
- Timeout de inactividad de conexiones: la página de troubleshooting dice "implement ping/pong keepalives" sin dar número `[M0]` (el stream silencioso vivió > 180 s antes de que la suspensión lo cortara).
- **Respuesta temprana sobre un stream h2 a medio abrir** (**medido 2026-09-15**, M2): si la app responde a un RPC (cabeceras + trailers, p. ej. `UNAUTHENTICATED` desde una capa que no lee el body) antes de consumir el body de la petición, hyper cierra el stream con `RST_STREAM` y el cliente recibe **`RST_STREAM(CANCEL)`** del proxy en vez de la respuesta: grpcio lo presenta como `CANCELLED`. Es una carrera (M1 pasó dos veces con el mismo código); `rayd` drena el body de toda petición rechazada (≤ 1 MiB, ≤ 2 s) antes de responder. **medido 2026-09-15 (M3, §16 Q33)**: en un client-stream (`FilesystemService.Write` a una ruta denegada) el drenaje basta cuando el resto del body cabe en su tope (1 B → `PERMISSION_DENIED` 6/6); si el cliente sigue enviando cuando el servidor responde (4 MB a 0,65 MB/s de subida) el proxy vuelve a entregar `RST_STREAM(CANCEL)` 6/6 y el status se pierde. Con h2 el servidor no tiene otra salida que consumir el body entero.
- Apps que escuchan sólo en `127.0.0.1`: **el proxy las alcanza** vía `X-aws-proxy-port` (**medido 2026-09-15**: `GET /` a un listener en `127.0.0.1:3000` → 200). No hace falta forwarder.
- PrivateLink: `com.amazonaws.<region>.lambda` para la API de control; `com.amazonaws.<region>.lambda-microvm` para el tráfico a endpoints (SNI y `Host` deben seguir siendo el hostname del MicroVM). Política de endpoint evaluada contra `lambda:ConnectMicrovm` con `Principal "*"`.

## 8. Lifecycle hooks

Fuente: <https://docs.aws.amazon.com/lambda/latest/dg/microvms-launching.html> (OpenAPI "Lambda MicroVMs Application Hook Interface" 2025-12-03),
<https://docs.aws.amazon.com/lambda/latest/dg/microvms-images.html>, `docs/aws-api/model_summary.md` (Hooks),
<https://docs.aws.amazon.com/help-panel/lambda/latest/console/lambda-microvm-image-create-lifecycle-hooks.html>.

Configuración en `create-microvm-image`:

```json
"hooks": {
  "port": 9000,
  "microvmImageHooks": { "ready": "ENABLED", "readyTimeoutInSeconds": 600,
                         "validate": "ENABLED", "validateTimeoutInSeconds": 600 },
  "microvmHooks": { "run": "ENABLED", "runTimeoutInSeconds": 30,
                    "resume": "ENABLED", "resumeTimeoutInSeconds": 30,
                    "suspend": "ENABLED", "suspendTimeoutInSeconds": 30,
                    "terminate": "ENABLED", "terminateTimeoutInSeconds": 10 }
}
```

| Hook | Momento | Path (todos **POST**, en `hooks.port`) | Body | Códigos | Timeout |
|---|---|---|---|---|---|
| `/ready` | build, tras arrancar `CMD`; señala que se puede snapshotear | `/aws/lambda-microvms/runtime/v1/ready` | ninguno | 200 ok; **503 = reintentar** (responder inmediatamente, no bloquear) | 1–3600 s |
| `/validate` | build, en una VM nueva desde el snapshot; AWS muestrea páginas tocadas para prefetch | `.../validate` | ninguno | 200 / 503 reintentar | 1–3600 s |
| `/run` | tras arrancar un MicroVM desde el snapshot; **el tráfico sólo llega después del 200** | `.../run` | `{"microvmId": "...", "runHookPayload": "..."}` | 200 | 1–60 s |
| `/resume` | tras restaurar; la VM sigue `SUSPENDED` hasta el 200 | `.../resume` | ninguno | 200 | 1–60 s |
| `/suspend` | antes del checkpoint | `.../suspend` | ninguno | 200 | 1–60 s |
| `/terminate` | antes de liberar recursos | `.../terminate` | ninguno | 200 | 1–60 s |

- `hooks.port` es un entero 1–65535 **sin valor por defecto en la API**; "si configuras cualquier hook debes indicar el puerto". La consola y todos los ejemplos de AWS usan **9000**; el sample multi-tenant usa 8080 compartido con la app (funciona, pero expone los hooks a cualquier token del puerto 8080). **medido 2026-09-15**: **cualquier puerto de hooks es alcanzable desde fuera** con un token `allPorts` o que incluya ese puerto (`POST :9000/…/ready` vía proxy → 200), porque el proxy vive dentro de la VM. Nunca emitir tokens que cubran el puerto de hooks.
- Cómo llegan los hooks (**medido 2026-09-15**): desde `127.0.0.1`, **HTTP/1.1**. `/ready` (build) lo llama un cliente `smithy-java/1.6.0` con `x-amzn-requestid` y `Host: <endpoint de la VM de build>`; `/run`, `/suspend` y `/resume` llegan con `host: localhost:9000`, sin user-agent, y `/run` con `content-type: application/json` y body `{"microvmId": …, "runHookPayload": …}`. `/validate` corre en una VM desechable: nada de lo que haga queda en el snapshot.
- Un hook `DISABLED` (default) no se invoca aunque esté implementado. Si se usa algún `microvmHooks` hay que implementar también `/ready`.
- Defaults cuando está `ENABLED` sin timeout: 30 s (ready/validate) y **1 s** (runtime), según la guía interna de AWS (skill del Agent Toolkit); no aparece en docs públicas `[M0]`. **Fijar siempre timeouts explícitos.**
- Los hooks de runtime se ejecutan bajo el execution role; los de build bajo el build role.
- Escuchar en `0.0.0.0` (los hooks llegan desde `127.0.0.1`, pero no se ha probado un listener ligado sólo a loopback `[M0]`). AWS llama a los hooks con **HTTP/1.1** (**medido 2026-09-15**).
- **Hacer `/suspend` y `/terminate` idempotentes** por precaución (no se observaron reintentos). Si `/run` falla o agota el timeout, la VM pasa directa a `TERMINATING` con `stateReason`. **Si `/suspend` devuelve 500 la VM se termina** (**medido 2026-09-15**, `stateReason` "Suspend lifecycle hook returned HTTP status 500…"), al contrario de lo que sugiere troubleshooting: `rayd` responde 200 a `/suspend` siempre y hace el trabajo con `timeout` interno.
- Patrón probado por aws-samples: `/run` devuelve 200 **rápido** y hace el trabajo lento en background; `/ready` responde 503 hasta que la app está lista, con una válvula de escape por tiempo para no bloquear builds.

## 9. Credenciales y entorno dentro del MicroVM (**medido 2026-09-15**)

Las credenciales del `executionRoleArn` se sirven por **IMDSv2** en `http://169.254.169.254/latest/meta-data/iam/security-credentials/execution_role` (primero `PUT /latest/api/token` con `X-aws-ec2-metadata-token-ttl-seconds`; el listado de `…/security-credentials/` devuelve exactamente `execution_role`). `LastUpdated` = instante del `run-microvm`, `Expiration` = +55 min. No hay `AWS_ACCESS_KEY_ID` ni `AWS_CONTAINER_CREDENTIALS_*` en el entorno. Variables inyectadas: `AWS_LAMBDA_MICROVM_IMAGE_NAME`, `AWS_LAMBDA_MICROVM_IMAGE_ARN`, `AWS_LAMBDA_MICROVM_IMAGE_VERSION`, `AWS_REGION`.

Entorno del proceso de la app: uid 0 con capabilities capadas (`CapEff` = chown, dac_override, fowner, fsetid, kill, setgid, setuid, setpcap, net_bind_service, net_raw, sys_chroot, mknod, audit_write, setfcap; **sin** sys_admin, net_admin ni sys_ptrace), `/sys/fs/cgroup` no montado, `iptables` instalado pero inutilizable sin `additionalOsCapabilities`, `setpriv`/`runuser`/`su`/`useradd` disponibles, `sudo` ausente, `RLIMIT_NOFILE` 1024, kernel 6.1.166 amzn2023 aarch64, raíz ext4 de 8 GB en `/dev/vdc`, cgroup de PID 1 `0::/system.slice/app`.

Consecuencias:
- **Cualquier proceso dentro de la VM, incluido el código del agente, puede leer esas credenciales** (IMDS responde igual a uid 1000). Por defecto Rayito lanza **sin** execution role. **M6 (medido 2026-09-16, §16 Q48)**: en la variante `rayito-base-caps` (`additionalOsCapabilities: ["ALL"]`) `rayd` bloquea IMDS para uid 1000-65535 con una ruta de política (`ip rule uidrange` + `blackhole 169.254.169.254/32`; `iptables -m owner` no existe en el guest) y `Health.imds_blocked` lo confirma: `PUT /latest/api/token` como uid 1000 → `EINVAL` en 0,3 s, root sigue llegando, el bloqueo sobrevive a suspend/resume. El agente de la plataforma usa uids 991-994 y su propio canal a IMDS: no se puede bloquear "todo lo que no sea root".
- **`RLIMIT_NOFILE` no se puede subir** (**medido 2026-09-15**, M2): el proceso de la app hereda soft=hard=**1024** y, aunque corre como uid 0, `CapEff` no incluye `CAP_SYS_RESOURCE`, así que `setrlimit(RLIMIT_NOFILE, 4096, 4096)` falla con `EPERM` incluso antes de `setuid`. `rayd` recorta al hard heredado (1024/1024); `RLIMIT_NPROC` 512 y `RLIMIT_CORE` 0 sí se aplican. Subirlo exigiría `additionalOsCapabilities: ["ALL"]` (M6).
- Tras `resume` (313 s suspendida) IMDS sirve **las mismas credenciales** (mismo `AccessKeyId`, misma `Expiration`), aún válidas. Si las rota al acercarse el vencimiento sigue sin medir `[M0]` (haría falta una suspensión > 55 min); asumir que sí, como en EC2, pero no depender de ello.

## 15. Semántica del snapshot (imagen y suspend)

Fuente: <https://docs.aws.amazon.com/lambda/latest/dg/microvms-images-snapshots.html>,
<https://docs.aws.amazon.com/lambda/latest/dg/microvms-best-practices.html>, docs de Firecracker (`snapshot-support.md`, `random-for-clones.md`).

- Sobrevive: memoria de todos los procesos (daemons, hijos), disco, descriptores, pipes, sockets Unix y TCP loopback (estado del kernel invitado), PTYs, inotify.
- **Se matan todas las conexiones salientes no locales** en run y en resume. Las entrantes (proxy → app) se pierden: el cliente debe reconectar.
- Reloj (**medido 2026-09-15**): **AWS corrige el reloj de pared** al reanudar (UTC en la VM vs real: −1 s tras 313 s suspendida) **y `CLOCK_MONOTONIC` también avanza** el tiempo suspendido (Δwall 313.15 s, Δmono 313.14 s entre `/suspend` y `/resume`; un `time.sleep(120)` lanzado 35 s antes de suspender terminó nada más reanudar). Consecuencia: los timeouts de tokio/`sleep`/keepalive **sí vencen** durante la pausa. Decisión M5 (`ARCHITECTURE.md` "Reloj de ejecución"): los plazos del agente (procesos, PTYs, ejecuciones, retención) se miden en **tiempo de ejecución** = monotónico − suspendido (`SandboxSession::running_now`, `Deadline`, `running_sleep`), sin rearme explícito; **medido 2026-09-16 (§16 Q41)**: `timeout=25` con 31.9 s de pausa vence 22.6 s después del resume y `clock_offset_ms` = 0 tras cada ciclo (AWS mueve pared y monotónico a la par).
- Unicidad: todo lo generado antes de `/ready` (tokens, UUIDs, semillas PRNG de Python/numpy, clave HMAC del kernel de Jupyter) es idéntico en cada MicroVM y en cada resume (**medido 2026-09-15**: `random.random()` evaluado al importar valió 0.5693094545201111 en dos VMs distintas de la misma versión; `os.urandom` sí difiere). Generar material per-VM en `/run`; reseed en `/run` y `/resume`; usar `OsRng`/`/dev/urandom` por llamada. La VM reseed el CRNG del kernel vía VMGenID (ARM64 con kernel 6.1 `[M0]`).
- Coste/latencia: memoria restaurada eager, disco bajo demanda; "≈1 s por cada 500 MB de snapshot leído". Un snapshot con pandas/matplotlib precargados es más lento de arrancar y reanudar; `/validate` debe ejercitar el camino real para que AWS prefetchee esas páginas. **Medido 2026-09-15 (M4, §16 Q35)**: con 925 MB de memoria y 1,29 GB de code install, `run-microvm` → `Health.agent_ready` sigue en ≈ 2 s, pero el primer proceso Python que arranca tras el restore (el reinicio del kernel en `/run`) tardó **45 s** cuando `/validate` no lo había ejercitado (6.0) y **2–4 s** cuando sí (7.0/8.0): lo que `/validate` no toca se lee del disco perezoso a demanda. **Medido 2026-09-16 (M6, §16 Q42, `docs/benchmarks/2026-09-cold-start.md`)**: el tamaño del snapshot pesa poco en el restore (`agent_ready` p50 2,33 s con 919 MB frente a 1,84 s con 694 MB: una diferencia de 0,5 s que queda dentro de la resolución de esa sonda —hasta ≈ 0,4–0,7 s por valor, informe §1— y que por tanto **no** da una pendiente por 100 MB); lo que domina el cold start es lo que el reinicio del kernel en `/run` vuelve a ejecutar: con el warm-up, `kernel_ready` p50 5,20 s; sin él (`rayito-base-slim` 2.0) 2,99 s, a cambio de 0,65 s más en la primera celda que importe pandas + matplotlib (0,79 s frente a 0,14 s).

## 17. S3 desde el MicroVM (`m7-s3-persistence`, **contrato de parámetros**)

`rayd` (uid 0, credenciales del execution role por IMDSv2, §9) usa Amazon S3
para `FilesystemService.Checkpoint`/`Restore` (ADR-009). **Estas son las únicas
operaciones y los únicos parámetros de S3 que `rayd` puede enviar**: la regla
dura 1 (`openspec/project.md`) vale también aquí. Fuente: Amazon S3 API
Reference (URL por operación). Cliente `aws-sdk-s3` con
`BehaviorVersion::latest()`, región de `S3Location.region` o `AWS_REGION`
(§9), `force_path_style` sin fijar, reintentos por defecto (3 intentos), sin
endpoint personalizado. Sin `ServerSideEncryption`, `StorageClass`,
`Metadata`, `ChecksumAlgorithm` ni ACL: aplican los valores por defecto del
bucket (SSE-S3 desde 2023; la política del bucket es del operador).

| Operación | Parámetros que envía `rayd` | Para qué | Referencia |
|---|---|---|---|
| `HeadObject` | — | **No se usa** (listada para decirlo: la ausencia del manifest se detecta con el `NoSuchKey` de `GetObject`) | <https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html> |
| `GetObject` | `Bucket`, `Key` | descarga de `<key_prefix>/manifest.json` y de `<key_prefix>/home.tar.gz` | <https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html> |

No hay `ListObjectsV2`: `s3:ListBucket` se concede en `spike/m0/iam.yaml`
sólo para que una clave ausente responda `404 NoSuchKey` en vez de `403
AccessDenied` (<https://docs.aws.amazon.com/AmazonS3/latest/API/API_GetObject.html#API_GetObject_Errors>),
de lo que depende el `NOT_FOUND` del restore. Códigos de error que `rayd`
clasifica (campo `Code` del cuerpo XML, expuesto por el SDK como
`ProvideErrorMetadata::code()`): `NoSuchKey`/`NoSuchBucket` → `not_found`,
`AccessDenied`/`ExpiredToken`/`InvalidAccessKeyId` → `permission_denied`,
`PermanentRedirect` (301, bucket en otra región) → `invalid_argument`,
cualquier otro → `internal` (con `s3_error_code` y `s3_request_id` en el log).

`s3:AbortMultipartUpload` sobre `arn:aws:s3:::<bucket>/<prefix>/*` y
`s3:ListBucket` sobre el bucket con `s3:prefix` = `<prefix>/*`
(<https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-with-s3-actions.html>).
