## Context

Design spec §5 and §6 of the AI agent phase (fast start). The facts it
relies on were measured in the design stage (2026-10-06):

- F1: `opencode serve` loads its config per directory instance, lazily, on
  the first request for that directory. A server warmed on one directory
  and then attached with `--dir <workdir>` reads the config as it is at
  that moment, so serve-in-pool needs no `rayd` change even though the
  gateway port is only known at `take()`.
- F2: `PATCH /config` does nothing under `OPENCODE_CONFIG`; not used.
- F3: the server uses basic auth from `OPENCODE_SERVER_PASSWORD`;
  `/global/health` and `/config` are the endpoints the warm-up uses.
- Spike (docs/research/2026-10-agent-spike.md): the recipe, pins, sizes,
  build ≈ 277 s, OpenCode RSS 575 MiB.

## Goals / Non-Goals

**Goals:** one SDK call and one CLI command build the agent image; a pool
can prepare and close slots for the agent; all four fast-start options
(A prefetch, B resume, C warm pool, D serve-in-pool) are measurable by the
acceptance stage.

**Non-Goals:** choosing the default between C and D (gates G1/G2 belong to
the AWS stage); the deepagents runner itself (`ai-agent-deepagents`); the
docs (`ai-agent-docs-pricing`).

## Decisions

- **D1 — `AgentTemplate` composes `Template`, it does not subclass it.**
  `to_template()` returns a plain `Template`, so `to_dockerfile()`, the
  build path and its IAM are exactly those of `Template.build`. The build
  context (manifest, requirements, prefetch script) is written to a
  temporary directory and passed as `context_dir`; it is removed after the
  build. The recipe lives in `_template.py` rather than each adapter's
  `template_steps()`: both runtimes' steps share the install dir, the
  ownership fix-up and the smoke test, and one shared vector file
  (`testdata/agent/agent-template/cases.json`) pins the result in both
  SDKs.
- **D2 — One source for the deepagents requirements.** The hash-locked file
  moves to Python package data; its sha256 goes in `limits.json` and the
  recipe checks it with `sha256sum -c` before `pip install
  --require-hashes`. TypeScript gets the bytes from a generated module
  (`gen_agent_template_assets.py --check` in CI). The local Docker variant
  copies the same file through `additional_contexts`.
- **D3 — Prefetch is a daemon driven by wall-clock jumps.** `rayd` starts
  `start_cmd` before the build snapshot, so it is alive in every VM born
  from the image. A jump above 30 s between 2 s sleeps can only be a
  restore (launch or resume, AWS_API_NOTES §15); it then reads the
  manifest's `prefetch_paths` with `nice -n 19` and imports deepagents once.
  It never writes and never touches the network. G1 decides whether it
  stays on by default.
  The AWS acceptance (Q146) showed the reads competing with the boot:
  `create()` p50 8.7 s → 16.6 s. The daemon now waits, after the jump,
  until `/proc/diskstats` shows no I/O in flight for 1 s (at most 60 s):
  the default kernel rotation that `create()` waits for reads from the
  code disk, so the quiet window starts once the VM is ready. After that it
  reads without yielding, because the first `opencode run` reads the same
  binary and a sequential read ahead of its page faults helps rather than
  competes. `ionice` was rejected (no effect without a BFQ/CFQ scheduler
  on the virtio disk), and so was a `rayd` readiness marker (a Rust and
  base-image change for the same signal).
- **D4 — Pool warm-up runs between settle and pause.** Foreground steps use
  `commands.run(timeout=step.timeout_seconds, max_output_bytes=0)`, so a
  non-zero exit (`CommandExitException`) or a timeout fails the warm-up
  through the existing path (terminate, backoff, `failed += 1`). Background
  steps use `background=True, timeout=None, max_output_bytes=0` and the
  handle is disconnected; the process keeps running into the snapshot.
  Recycling relaunches the slot and re-runs the steps, so each VM gets its
  own serve password (§15 uniqueness).
- **D5 — The serve password lives only in the VM.** It is generated by the
  warm-up inside each VM (`/dev/urandom`, 0600, uid 1000) and parked in the
  snapshot with the same custody as the slot's access token (T14).
  `SlotRecord` and `rayito.pool/1` are unchanged.
- **D6 — Serve needs a config file before the gateway exists.** The first
  serve step writes a placeholder `{"$schema": …}` only if no config is
  there; `agent.run` overwrites it after `take()` and, because the applied
  sha differs, disposes the workdir instance before attaching.
- **D7 — Egress is per pool.** `PoolConfig.allow_internet_access` and
  `network` are validated with the same rules as `create()` and only appear
  in the launch kwargs when set, so existing pools launch exactly as before.
  `create(pool=…)` keeps rejecting a per-call network.
- **D8 — `agent.prepare()` starts background steps without a timeout.** A
  `timeout` on a background `opencode serve` would kill it after 120 s.

## Risks / Trade-offs

- The prefetch benefit and the serve benefit are unmeasured until the AWS
  stage (Q146–Q148); both stay opt-in at the pool level and the pool size
  default stays 0.
- A larger parked snapshot costs more per recycle cycle (≈ $0.78 C,
  ≈ $0.92 D per slot-month vs $0.60 base, list prices 2026-10-06).
- Whether a managed background process survives suspend/resume is measured
  in Q148 (§15 says loopback survives).
